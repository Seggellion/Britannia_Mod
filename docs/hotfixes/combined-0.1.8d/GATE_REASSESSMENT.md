## Performance risk and evidence

The fence adds 2,048 registered states/cache entries, 28 loaded SimpleBakedModels and 1,248 quads. Selector count is not independent mesh count. Three GC histograms per comparable original baseline/hotfix client establish stable counts and median total Java heap increase **8,719,176 bytes (8.32 MiB, 1.75%)**. Sample ranges are 44,624 and 28,624 bytes. These totals do not isolate exclusive fence retained size or native/GPU memory. See [original measurements](../../projects/patch18-edge-fence-hotfix/COST_MEASUREMENTS.md).

One original comparable startup pair was 34.999/34.596 seconds; resource reload was 9.740/8.520 seconds. Those include other initialization/resources, do not isolate model bake, and establish neither repeat variance nor improvement. No established absolute release threshold or demonstrated timing/frame failure was found. The playbook asked for measurements and explicitly rejected arbitrary unsupported percentage limits. Earlier milestone language elevated unfinished repetitions to a hold; the owner's current reassessment supersedes that designation without changing the measured cost.

Repeated matched startup, isolated bake and representative frame profiling remain useful follow-up. Meaningful GPU/client timing would start/render clients and interfere with the desktop, so it is not executed under the current instruction. Dedicated-server launch logs are preserved for identity/persistence, not passed off as client model-bake/frame benchmarks. The optional bake instrumentation source is retained, unattached to the candidate. No timing regression is concealed and no invented threshold is used.
