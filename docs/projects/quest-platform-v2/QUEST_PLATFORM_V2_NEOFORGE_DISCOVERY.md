## Rails-facing transport

The client-action path is `QuestProxyService.handle` -> `resumeAfterJournalRefresh` when needed -> `dispatch`, which submits `callRails` through `ServerHttpExecutor.submit`; `callRails` resolves the endpoint, builds JSON, attaches authentication, POSTs, bounds the response, and parses it to `Result`; `completeAction` routes a hand-in demand or calls `applyAuthoritativeResult`/`applyQuestResponse`; `send` returns a `QuestActionResultS2CPayload`. Sources: `src/main/java/com/seggellion/britannia_mod/quest/QuestProxyService.java` methods `handle`, `resumeAfterJournalRefresh`, `dispatch`, `callRails`, `completeAction`, `applyAuthoritativeResult`, `applyQuestResponse`, and `send`; `src/main/java/com/seggellion/britannia_mod/server/http/ServerHttpExecutor.java` `submit`.

Server-originated legacy calls are built by `QuestServerAPI.recordKill`, `sendTrigger`, and `quitQuest`; common `post` performs the request, `postQuest`/`postQuit` parse typed answers, and `submit` places work on the HTTP executor and returns to the server thread. Sources: `src/main/java/com/seggellion/britannia_mod/quest/network/QuestServerAPI.java` methods named in this sentence.

The journal-refresh path begins in `QuestJournalRefresh.refresh`, which submits its default fetcher, `fetchFromRails`, through `ServerHttpExecutor.submit`. `fetchFromRails` resolves `Endpoint.QUEST_JOURNAL` plus `player_uuid` through `ServerCredentials.apiUrls().resolvePath`, configures a bounded `HttpURLConnection` GET with JSON acceptance, authenticates the bodyless request through `RailsRequestAuthenticator.apply`, reads the bounded JSON response, and parses it with `QuestEntryParser.parseAcceptedQuests`. `refresh` returns completion to the server thread, where `QuestJournalRefresh.complete` installs successful state with `ServerQuestTable.replaceFromBootstrap`, invokes the journal-refresh reconcilers and material guidance, and then runs the queued callbacks. Sources: `src/main/java/com/seggellion/britannia_mod/quest/QuestJournalRefresh.java` methods `refresh`, `fetchFromRails`, and `complete`; `src/main/java/com/seggellion/britannia_mod/server/http/ServerHttpExecutor.java` `submit`; `src/main/java/com/seggellion/britannia_mod/quest/QuestEntryParser.java` `parseAcceptedQuests`; `src/main/java/com/seggellion/britannia_mod/quest/ServerQuestTable.java` `replaceFromBootstrap`.

The base URL originates in `ServerCredentialSource.load`: environment credential mode requires `ULTIMACRAFT_API_BASE_URL`; file credential mode uses a non-empty `ULTIMACRAFT_API_BASE_URL` as an override and falls back to `api_base_url` from `config/britannia_mod-server.properties`. `RailsApiUrlResolver.normalizeServiceOrigin` normalizes it, `ServerCredentials.apiUrls()` exposes the resolver, and the proxy/action/delivery/hand-in/reissue clients call its endpoint-specific `resolve*` methods. Sources: `src/main/java/com/seggellion/britannia_mod/server/auth/ServerCredentialSource.java` `load`; `src/main/java/com/seggellion/britannia_mod/server/http/RailsApiUrlResolver.java` `normalizeServiceOrigin` and `resolve*`; `src/main/java/com/seggellion/britannia_mod/server/auth/ServerCredentials.java` `apiUrls`; `QuestProxyService.callRails`; `QuestActionEventClient.execute`; `QuestRewardDeliveryClient.executeAcknowledge`/`executePending`; `QuestItemHandinClient.executeConfirm`/`executeReconcile`; `QuestEquipmentReissueService.post`.

`RailsRequestAuthenticator.apply` attaches `Shard-Name` and `Shard-Secret`; its body overload also calls `RequestSignature.applyTo`, which attaches `X-Signature-Timestamp`, `X-Signature-Nonce`, and `X-Signature`. The action-event, reward-delivery, and hand-in clients additionally attach `Minecraft-Server-Key`. Equipment reissue does not attach that header: `QuestEquipmentReissueService.post` sets `Content-Type` and `Accept`, then calls `RailsRequestAuthenticator.apply`. Sources: `src/main/java/com/seggellion/britannia_mod/server/auth/RailsRequestAuthenticator.java` `apply`; `src/main/java/com/seggellion/britannia_mod/server/auth/RequestSignature.java` `applyTo`; `src/main/java/com/seggellion/britannia_mod/quest/action/QuestActionEventClient.java` `execute`; `src/main/java/com/seggellion/britannia_mod/quest/delivery/QuestRewardDeliveryClient.java` `executeAcknowledge`/`executePending`; `src/main/java/com/seggellion/britannia_mod/quest/handin/QuestItemHandinClient.java` `executeConfirm`/`executeReconcile`; `src/main/java/com/seggellion/britannia_mod/quest/equipment/QuestEquipmentReissueService.java` `post`.

Response parsing and dispatch are split by surface: `QuestProxyService.callRails` uses Gson and dispatches through `completeAction`; `QuestServerAPI.postQuest` uses Gson into `QuestModels.QuestResponse`; `QuestActionEventProtocol.parse`, `QuestRewardDeliveryProtocol.parseResult`, `QuestRewardDeliveryParser.parseTransition`/`parsePendingListing`, and `QuestItemHandinProtocol.parseConfirmation`/`parseReconcile` validate the specialized v1 bodies before their client `classify*` methods return typed results to dispatcher/service/reconciler callbacks. Sources: the named methods in their files under `src/main/java/com/seggellion/britannia_mod/quest/`.

## Existing effect, delivery, hand-in, and reissue machinery

There is no generic v2 effect-occurrence store or codec in this tree. The existing occurrence-like identity is the v1 action `event_uuid`, minted locally with `UUID.randomUUID()` in `QuestActionDispatcher.publish` and stored as `EventUuid` by `QuestActionOutboxEntry.toNbt`; request attempts mint a separate request UUID in `QuestActionDispatcher.attempt`. Sources: `src/main/java/com/seggellion/britannia_mod/quest/action/QuestActionDispatcher.java` `publish` and `attempt`; `QuestActionOutboxEntry.toNbt`; command `Get-ChildItem ... | Select-String 'effect_occurrence'` returned no quest implementation. This observation does not answer OD-07.

Achievement granting is an existing authoritative effect path: `QuestProxyService.applyQuestResponse`, `QuestActionDispatcher.installState`, and `QuestObjectiveWatcher.applySuccess` call `QuestAchievementAward.grantAndFilter`. `QuestObjectiveWatcher.applySuccess` is the legacy-observer path for a Rails deployment without `/api/v2/quest_action_events`: after an accepted location, pickup, or destroy objective response, it applies rewards; removes the completed quest or updates its objective triggers; grants and filters achievements; and forwards the filtered result to the client. `QuestAchievementAward.grant` calls `PlayerAdvancements.award` for each criterion, and `grantAndFilter` removes an already-earned achievement from the forwarded `client_actions`. The persisted advancement criterion is the existing per-player first-time token for replay suppression; this records its current role and does not assign it a v2 identity. Sources: `src/main/java/com/seggellion/britannia_mod/quest/QuestProxyService.java` `applyQuestResponse`; `src/main/java/com/seggellion/britannia_mod/quest/action/QuestActionDispatcher.java` `installState`; `src/main/java/com/seggellion/britannia_mod/quest/QuestObjectiveWatcher.java` `onPlayerTick`, `onItemPickedUp`, `onQuestItemDestroyed`, `send`, and `applySuccess`; `src/main/java/com/seggellion/britannia_mod/quest/achievement/QuestAchievementAward.java` methods `grantAndFilter`, `grant`, and `withoutAnnouncements`.

Delivery is implemented by `QuestRewardService`, every class in `quest/delivery/`, and `PlayerDataStore`'s applied marker. `delivery_uuid` is not produced by NeoForge: `QuestRewardDeliveryParser.parseDelivery` reads it from Rails' `delivery_uuid`; `QuestRewardDeliveryLedgerEntry.toNbt` stores it as `DeliveryUuid`; `PlayerDataStore.markDeliveryApplied` stores its string in `applied_delivery_uuids`; `QuestRewardDeliveryProtocol.encodeResult` returns it in an acknowledgement. Sources: those exact methods in `QuestRewardDeliveryParser.java`, `QuestRewardDeliveryLedgerEntry.java`, `PlayerDataStore.java`, and `QuestRewardDeliveryProtocol.java`.

Hand-in is implemented by every class in `quest/handin/`, entered from `QuestProxyService.completeAction` when `QuestItemHandinService.isHandinRequired` succeeds. `QuestItemHandinProtocol.parseDemand` reads Rails' `handin_uuid`; `QuestItemHandinService.begin` locally mints a distinct `requestUuid` with `UUID.randomUUID()` only when a ledger row does not already provide one; `QuestHandinLedgerEntry` and `PlayerDataStore.HandinRemovalMarker` store that transaction/correlation identity and concrete removal proof. Sources: the named methods/types in `QuestProxyService.java`, `QuestItemHandinProtocol.java`, `QuestItemHandinService.java`, `QuestHandinLedgerEntry.java`, and `PlayerDataStore.java`.

The existing refund/compensation anchor is recorded, not redesigned here: `QuestItemHandinProtocol.parseRefundDeliveryUuid` reads Rails' `refund_delivery.delivery_uuid`; the `CANCELLED_REFUNDED` path settles the hand-in as `REFUNDED`, while refund items flow through the ordinary reward-delivery machinery. The hand-in row does not store a separate refund UUID; its durable evidence is Rails' `handin_uuid` plus locally stored `Proof` in the hand-in ledger/player marker. Sources: `QuestItemHandinProtocol.ConfirmationResponse` and `parseRefundDeliveryUuid`; `QuestItemHandinService.apply`/`settleRow`; fields and `toNbt` in `QuestHandinLedgerEntry`; `PlayerDataStore.HandinRemovalMarker`; `QuestRewardDeliveryService.apply`.

Reissue is the existing bounded equipment path: `QuestEquipmentReissuePolicy` decides eligible/missing tutorial equipment and `QuestEquipmentReissueService.request`/`callRails`/`post` posts a signed request; a granted `QuestRewardDelivery` is applied with `QuestRewardDeliveryService`. Sources: `src/main/java/com/seggellion/britannia_mod/quest/equipment/QuestEquipmentReissuePolicy.java`; `src/main/java/com/seggellion/britannia_mod/quest/equipment/QuestEquipmentReissueService.java` methods `request`, `callRails`, `post`, and `parse`.

None of the preceding identities supplies D-0086 activation encoding, OD-07 effect occurrence, or OD-08's hand-in bridge. Sources: `.uc/context/context/contracts/quest_contract_v2.md` open/deferred rows; the concrete v1 sources named in this section.
